# H100 run (T25)

One command runs everything on a rented GPU box and leaves one folder to copy back.

Target: E2E Networks, 1x H100 80GB, root access. The `budget2` stage also needs a
second GPU, so it runs only on a 2x H100 box (`--gpus 2`); on one GPU it is skipped.

## Before you book

1. Dry run anywhere: `bash scripts/h100_run.sh --dry-run`. Every number it prints is
   SIMULATED, and it should end with `exit: 0`.
2. Have a Hugging Face read token (`HF_TOKEN`) with the Llama 3.1 licence accepted on
   `meta-llama/Llama-3.1-8B-Instruct`. Muse Glimmer is Apache 2.0, so it needs no licence click.
3. Optional: `META_API_KEY`, so `--spark` makes one Muse Spark call to seed Optuna.
4. Disk: about 150 GB free (Glimmer BF16 is about 60 GB, Llama 8B is about 16 GB, plus the
   Docker image).

## On the box

```bash
git clone https://github.com/ak9381/wattnot && cd wattnot
export HF_TOKEN=...   # never committed, never printed
bash scripts/h100_run.sh --spark          # add --gpus 2 on a 2x H100 box
```

| Stage | What it does | Rough time on 1x H100 |
|---|---|---|
| setup | nvidia-smi, NVML, power-limit write, vLLM / Docker image, both models' weights, disk | 15-30 min (downloads) |
| probe | 10-minute go/no-go: cap write and readback, energy counter moves under load, mean power stays under a lowered cap, cap restored. Exit 20 on any failure | 5-10 min |
| sweep | 7 caps (700 to 400 W) x 5 reps per model, each gated against the 700 W baseline | 1.5-2 h |
| headline | FP8 + 2x batch vs baseline, 5 vs 5, gated, offline-signed receipt, per model | 30-40 min |
| best | fresh 5 vs 5 re-run of the lowest cap that passed, receipt, per model | 30 min |
| ablation | cold vs Spark-warm vs grid Optuna on the default model, 8 trials per arm, real objective | 1-1.5 h |
| budget2 | 2 GPUs at the best cap vs 700 W: same total work, freed rack watts, receipt | 30 min |

Models run in order: **Muse Glimmer 30B** (default, Meta open weights, BF16 on 1x H100),
**Muse Spark Open** (Meta open weights, NVFP4) and **Llama 3.1 8B** (comparison).
Muse Spark Open needs at least 700 GB of VRAM even in NVFP4 (Meta's model card), which is
more than 8x H100 80GB (640 GB). On a 1x H100 box the vLLM path is skipped and the reason is written
to `summary.json`; the llama.cpp side stage below runs it on one GPU instead. To tune it, run the same command on an 8x H200 141GB (or 8x B200) box:

```bash
bash scripts/h100_run.sh --gpus 8 --gpu-gb 141 --stages setup,probe,sweep,headline,ablation
```

On that box the per-GPU sweep caps still apply to every GPU, and one vLLM server spans all
8 GPUs (tensor + expert parallel). Muse Spark also plans each step through the Meta Model API.

If the probe fails, the script prints `PROBE FAILED: release the machine now.` and stops,
so we pay for at most about 10 minutes.

## What comes back

`results/h100-<time>/` and `results/h100-<time>.tar.gz`:

- `setup.json`, `probe.json`: the checks and the go/no-go evidence
- `sweep.csv`: model, cap, Wh/request, Wh per 1k tokens, p99, label, gate result
- `runs/<run_id>/`: `run.json` and the event log for every gated comparison
- `receipts/`: hash-chained receipts and their offline signature bundles
- `traces/`: the 10 Hz NVML CSVs each receipt points at by SHA-256
- `ablation.json`, `summary.json`, `logs/` (vLLM), `MANIFEST.sha256`

Labels: a window is MEASURED only when the NVML energy counter moved; otherwise it is
ESTIMATE. Fake-rig output is always SIMULATED. Water stays ESTIMATE.

The signing key is an offline test key in `~/.wattnot/test-key.pem`, outside the results
folder. Nothing is published to Rekor; that needs Akash's okay (T14/T20).

Copy back: `scp -r root@<host>:wattnot/results/h100-*.tar.gz .`

## Flex check (optional, about 10 minutes of GPU time)

Replaces the software model in `wattnot flex` with a real GPU. Run it after `probe` passes,
with a vLLM server already serving load. The load generator must append one JSON object per
second to a progress file:

```json
{"p99_ms": 2310.5, "pass_rate": 0.81, "rps": 9.8}
```

`wattnot flex load` writes that file for you. Start it first, in its own terminal, pointed at
the running server, and leave it up for the whole flex run (the first line appears within a few seconds). A dry run with `--fake` checks the plumbing with no
server and no GPU; it labels itself SIMULATED.

```bash
wattnot flex load --fake --duration 20 --progress /tmp/dry.jsonl          # dry run, no GPU
wattnot flex load --url http://127.0.0.1:8000 --model <served-model-name> \
  --rps 8 --progress /tmp/load-progress.jsonl                             # real load, Ctrl-C to stop
```

- Pick `--rps` so the GPU is busy but not saturated at full power (p99 flat before the event).
  Watch `p99_ms` in the file for a minute: if it keeps climbing, lower `--rps`.
- Latency counts from the moment a request was due, so a slowed GPU shows up in p99 instead of
  the generator quietly sending less.
- Quality is a small answer check on 27 bundled short questions (`data/flex/load-prompts.jsonl`,
  or `--prompts`). Every number it writes is MEASURED against that server; the check is coarse
  (the reply must contain an accepted answer), so call it a spot check, not a benchmark.
- A key, if the server wants one, goes in an environment variable named by `--api-key-env`.

```bash
wattnot flex run --backend gpu --progress /tmp/load-progress.jsonl --gpu 0 \
  --signal data/flex/grid-event-demo.json --event demo-evt-1 --out results/flex
wattnot flex show results/flex/<receipt>.json
```

- The event file is still a replayed, SIMULATED signal. The GPU readings in the receipt are
  MEASURED, so the receipt says both: `flex.label` MEASURED, `flex.signal.label` SIMULATED.
- It takes 30 s before + the event length (300 s) + 90 s after, in real time.
- A measured flex receipt grades ESTIMATE (no significance test), never VALID.
- The power limit is put back on exit, on an error, and on SIGTERM.
- Pass criteria: `status` full or partial with a stated `limit`; `p99_ms.sla_violation_s` of
  a few seconds at most; `pass_rate.event` within 1 point of `before`; cap restored.

## Optional: Muse Spark Open side stage (1x H100)

The full Spark Open (816B MoE, 42B active) does not fit in 80 GB of VRAM. A ready-made
Unsloth GGUF does fit in VRAM plus host RAM with llama.cpp, so the side stage runs it as a
**three-tier hybrid** and lets WattNot tune where the work lands:

| Tier | Where the weights are | Who does the maths | llama.cpp control |
|---|---|---|---|
| hot | VRAM | GPU | layers not covered by `--n-cpu-moe N` (all if N = 0) |
| warm | host RAM | GPU, after a copy over PCIe, when a batch has 32+ tokens (prefill, batched decode) | op offload, on by default; `-ub` sets how big each batch is |
| cold | host RAM | CPU, when a batch is under 32 tokens (normal decode) | `-t` threads; `--no-op-offload` makes every RAM layer cold |

Attention, shared experts and the KV cache always sit on the GPU (`--n-gpu-layers 99`).
Flags were checked against llama.cpp master (`common/arg.cpp`, `ggml-cuda.cu`) in Oct 2026.
The 32-token threshold is ggml's `GGML_OP_OFFLOAD_MIN_BATCH` default.

**Honest limit: the hot tier is per layer, not per expert.** In llama.cpp all 256 experts
of a layer are one stacked tensor, so `--n-cpu-moe` moves whole layers. We do not claim
router-frequency pinning. Per-expert pinning (colibri's VRAM expert cache, or a llama.cpp
patch) is a later stretch; `spark_open/placement.py` has the `ExpertPlacement` stub for it.

Knobs, each applied by restarting `llama-server`:

- **quant**: `UD-IQ2_S` (default, the agentic floor), `UD-IQ2_XXS`, `UD-IQ1_M`, `UD-IQ1_S`.
  Anything below IQ2_S is flagged: agentic tasks degrade.
- **hot layers** (`--n-cpu-moe`): 4 levels per quant, from 0 hot layers up to the most that
  fit in VRAM for that quant (about 14 for IQ2_S, 20 for IQ1_S; ESTIMATE from file size).
- **batch mode**: `gpu` = op offload on with `-ub 4096` (warm tier active), `cpu` =
  `--no-op-offload` with `-ub 512` (the CPU comparison). `--gpu-ubatch 512|2048|4096`
  changes the gpu-mode ubatch.
- **CPU threads** (`-t`, default 24, `--threads` on the stage CLI).

The planner builds 4 x 4 x 2 = 32 tries, grouped by quant so each quant downloads and
loads once, and drops the lowest-priority tries if the time estimate passes the budget:

```bash
# a recent llama.cpp build with CUDA, so llama-server is on PATH
bash scripts/h100_run.sh --spark --spark-open --spark-open-dir /data/spark-open \
  [--spark-open-budget-h 4.5]
```

- **Extra time:** planned at about 4.2 h for all 32 tries (ESTIMATE: 4 downloads at about
  10 GB/min, one cold load per quant, about 2 min per restart and 2.5 min per try). Plan
  details and any dropped tries are in `spark_open.json` under `plan`.
- **Disk:** at least 550 GB free on the models volume. The four quants total about 865 GB,
  so each non-baseline quant is deleted when its tries finish; disk holds `UD-IQ2_S`
  (about 260 GB) plus one other at a time.
- **RAM:** at least 200 GB (the E2E 1x H100 plan has 250 GB).
- If disk, RAM or `llama-server` is missing, the stage is skipped with the reason in
  `spark_open/spark_open.json`, and the core results are untouched.

**Energy is whole-node, per output token.** GPU joules come from NVML; CPU package and
DRAM joules come from RAPL (`/sys/class/powercap`). The objective is
(GPU J + CPU package J + DRAM J) / output tokens. With offload, GPU watts can fall just
because the CPU is doing the work. So:

- every receipt records the **CPU share of energy** (CPU+DRAM J / whole-node J) and the
  **per-tier split** (hot, warm, cold layer counts and the rules that apply);
- if GPU energy drops but CPU+DRAM energy rises by about as much, the try is flagged
  **shifted, not saved** and never counted;
- if the VM hides RAPL, every try is labelled **GPU-only ESTIMATE**, the CPU share is
  "unavailable", and no saving is counted.

The tier split is the configuration, not a measurement: how much work is warm vs cold
depends on the batch sizes the prompts produce. The VRAM figure per try is an ESTIMATE.

**Quality gate:** answers are compared with a reference config, and a try passes when
agreement drops at most 1 point and p99 stays within 10%. The default reference is the
local baseline (UD-IQ2_S, all experts on CPU, op offload off). A hosted full-precision
endpoint (Baseten or Modal) can be set with `WATTNOT_SPARK_REF_URL`,
`WATTNOT_SPARK_REF_PROVIDER`, `WATTNOT_SPARK_REF_KEY_ENV` (the name of the env var holding
the key) and `WATTNOT_SPARK_REF_ENABLE=1`. It is off by default and costs money per token
when on.

Every try writes a hash-chained record (knobs, tiers, GPU J, host J, CPU share, labels,
gate, shift check). The dry run (`--dry-run`) uses a fake backend and every number in it
is SIMULATED.
